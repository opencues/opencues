

This document re-states Command Stick inventions as solutions to specific problems
## The Problem
User Interfaces in the art have common problems:
Uses large amounts of screen space
Require dedicated screen or device space to be allocated to the UI, that cannot be used for
other tasks. In cases where there are many options, the UI may occupy most of the display,
leaving less space for the application (e.g. touch-screen buttons). This problem is particularly
onerous in devices with very small screens (e.g. smartwatches)
Requires visual attention
Require looking at the user interface, and away from the work / region of interest.
This may be because:
-User interfaces are often stateful, requiring the user to look at the user interface to know
its state. (e.g. menu, pages of buttons, caps lock)
-Items are not always displayed in the same location (e.g. recently used program menu)
-Do not provide non-visual feedback, requiring the user to look at the user interface to
know if an action has been performed correctly. (e.g. on-screen buttons)

-Have many activators that can only be differentiated by sight (e.g. buttons, keyboards,
menus)
-Are scale-dependent, so they cannot be utilised on smaller or larger screens.
-Attention is required to find the UI on screen, or to know the finger’s position on it or
relative to it (e.g. buttons, icons, on-screen keyboards).
## Slow
Execution takes time.
-Takes a long time to enter an input (e.g. words need multiple key strikes)
-Require multiple gestures to accomplish a task (e.g scrolling through list)
-Require large excursions to enter a command (e.g. menus)
-Cannot be performed quickly in response to an event (e.g. menus are bad for controlling
games)
Imposes a cognitive load
The cognitive load of using the UI reduces the user’s ability to perform a separate task whilst
using the user interface.
## Inexpressive
Are capable of only a few commands. (e.g. touch screen)
Not usable one-handed
require both hands. (e.g. keyboard)
Prone to errors
UIs can require movements that are difficult to perform with the required precision (e.g.
on-screen keyboards have small letters on a small screen, making it easy to press the wrong
key), or contain a large number of steps,with many options are prone to error.
Have no error-checking
actions are executed immediately, there is no way to confirm that this is what you want. (e.g.
pressing a mouse button causes the action)
Difficult to diagnose input errors
if the user makes an error, it can be hard for them to see and understand what went wrong.
(e.g. screen gestures are invisible)
Difficult to learn
require the user to reference the user interfaces text or instructions, even once the user is
experienced. (e.g. menus that have sub-menus)
-Unintuitive - not based on any existing or innate human faculty / ability
-Not apparent (e.g. shortcut keys)
-No affordance (e.g screen swiping)
-Lexicon not optimised for a specific human memory type (e.g. phonological loop needs
sound). Learning process not optimised for memory types (e.g. procedural memory
requires repetition)
-Many user interfaces are multiple single steps (e.g. keyboard), but procedural memory
requires a single unique movement.
Unnatural motion
-Unnatural motion types - Human hands evolved for grasping and fine-motor control
skills. Some input techniques do not take advantage of these techniques, instead using

coarse motion (e.g. swipes) or gestures the human hand does not naturally perform
(e.g. buttons, keys).
-Unnatural range - Many UIs require the user’s hands to move distances that stress the
user’s hands. Those distances may be longer than natural (e.g. keyboard), which
stresses the wrists,  or may be shorter than natural motion (e.g. on-screen keyboard),
which requires high concentration levels
Difficult to see
-User interface elements must be small because there are many of them. (e.g.
touch-screen keyboards)
-User interface elements require small labels because there are many or they are not
otherwise readily identifiable.
## Beautiful
To perform and observe (e.g typing)
Hand occlusion
The hand operating the user interface can occlude the input method (e.g. on a touch screen,
finger covers icon you are pressing)
Large separation
Input is distant from the work (e.g. keyboard), necessitating large gaze distance/ refocusing
between input and work to accomplish a task.
Not general purpose
Many user interfaces are suitable only for a specific task, so the skills learned are not
generalizable. (e.g. every program has a different menu, microwave ovens have different
buttons)
Ambiguous recipient
Most input methods can output to a range of targets.
It can be difficult to know what the recipient/target of a UI is (e.g. speech, text box focus).
Some UIs do not have a defined dedicated input area (e.g. touchpad or screen swipe
gestures) which make it difficult to know whether an input pertains to the active control or is
a device a command gesture (e.g. when a user swipes down, are they trying to scroll the
document or enable the status bar?)

How has this problem been solved before?
A large variety of human computer interfaces(HCI) systems have been invented to try solve
the problems detailed above:
Physical buttons
Adding physical buttons to a device requires sacrificing physical space. Procedural memory
developed on a specific physical button layout does not map to different button layouts.
To offer a large vocabulary of functionality with physical buttons multiple buttons are needed,
or a method for defining and detecting button press combinations is required. The button
press combination method is often hard to discover. This limits a user’s ability to explore the
available functionality.
Physical button layouts force a user to interact with a HCI in a fixed, unchangeable manner.
Unused physical buttons continue to take up physical space and inconvenience the user with
their presence.
## Mouse
A mouse or trackpad has a limited vocabulary of functionality outside translating and
interacting with onscreen elements. To achieve greater functionality other input systems
need to be used in conjunction with a mouse or trackpad. Navigating to elements on a page
is slow and inaccurate. The inconsistency in movements with a mouse makes it difficult for a
user to develop procedural memory.
It is difficult to discover what functionality can be offered by a mouse or trackpad beyond its
basic functionality. A mouse or trackpad are not cross platform HCIs and are only available
on a personal computing device. Different mice or trackpads have differing levels of
sensitivity which results in a user’s proficiency being inconsistent across different devices.
Mouse wheel
A mouse wheel has a limited vocabulary of functionality outside scroll or zooming. As the
mouse wheel is dependent on a mouse or trackpad, it is not possible to access a mouse
wheel without having a mouse or trackpad available. This limits its availability to personal
computer devices. Different mouse wheels have varying levels of sensitivity which leads a
user to having inconsistent experiences across different devices. The motion of using a
mouse wheel requires a degree of dexterity from a user due to a user having to perform an
unnatural scrolling motion repeatedly.
Dropdown menu
A dropdown menu’s size is a function of its complexity, this leads to a large amount of screen
space being necessary for it to be implemented in an application. Dropdown menus are
often docked in the top left or top right corner of a screen. This allows for the menu to
expand as much as necessary to display the available functionality.
It is difficult to implement a dropdown menu on mobile or watch interfaces due to them
having small screens. Dropdown menus are also slow to navigate and are difficult to build
procedural memory around due to them being error prone and having inconsistent layouts.
A designer may rearrange the layout of a dropdown menu which leads to a user being
confused.
Dropdown menus require a user to divert their attention from their current region of interest
to navigate and select functionality from a dropdown menu.
Due to dropdown menus needing a lot of physical space they often expand to occupy limited
screen space, this minimises a user’s ability to multitask.

## Slider
A slider has a limited vocabulary of functionality outside scroll or zooming. The affordance of
a slider also limits its potential use cases.
## Keyboard
Physical keyboards have inconsistent layouts across different keyboards and laptops. Digital
keyboards have inconsistent layouts across different screen sizes and software. The
inconsistency in keyboard layouts lower the transferability of a user’s procedural memory
across different keyboards.
Desktop, tablet, mobile and watch keyboards all have different layouts. A user is required to
build their procedural memory on each of them separately.
Keyboards are error prone and require a user to focus on entering the inputs correctly. This
diverts a user from the task at hand. Keyboards require a lot of space for them to be used.
Decreasing the size of a keyboard lowers the accuracy of a keyboard user’s inputs. A
keyboard requires predefined static regions for registering inputs.
To offer additional functionality on a keyboard, shortcuts need to be integrated. Keyboard
shortcuts are difficult to discover and are inconsistently implemented at the application and
device level. Multiple applications can have contradicting shortcuts which a user needs to
remember as they navigate between applications.
Additional functionality may also be added to a keyboard through adding more buttons,
however this increases the size of the keyboard.
Typing on keyboards is a strenuous unnatural motion and multiple excursions are necessary
to complete tasks on a keyboard.
Physical keyboards require a user to use both of their hands. This limits a user’s ability to
multitask whilst using a keyboard.
The functionality provided by a keyboard is dependent on the state of the system it is
connected to (e.g. Caps lock), this leads to a user having to constantly monitor a system's
state to correctly use a keyboard. Unused keys within a keyboard continue to take up
physical space or occupy limited physical screen space.
Touch screen/ digital buttons
Similar to physical buttons they have limited functionality. The functionality of a button may
be indicated to a user prior to an interaction. To achieve a large vocabulary of functionality a
button input system would need to introduce functionality which is low in discoverability such
as button press combos. Digital buttons compete for limited screen space with other visual
elements. Unused digital buttons continue to occupy limited screen size and cannot be
dismissed.
## Gesture
Traditional gesture systems struggle with discoverability and do not indicate to a user when
they are in a state of invalidity. This leads to a user being confused about whether their
partially constructed gesture is progressing towards a recognisable gesture.
The lack of discoverability in a traditional gesture system leads to a limited amount of
gestures being implemented.
The implemented gestures tend to focus on known shapes (e.g. a circle, triangle or square)
due traditional gesture systems lacking the necessary functionality to guide a user in
developing their procedural memory.
Gesture systems are error prone due to relying on path data to recognise the gesture and
because they provide a user within minimal guidance. Relying on path data leads to gesture
systems having to have a large degree of differentiation between gestures to ensure they
are accurately registered and not mistaken for another gesture.
Typical gesture systems tend to not have a confirmation phase where a user knows which
gesture will be performed prior to executing it. Traditional gesture systems are limited to

touch screen based applications due to a user having more dexterity with a touch screen
than with a mouse or trackpad.
The combination of being error prone, not providing a user with guidance and not indicating
the selected gesture prior to a function being executed, leads to gesture systems being
untenable on non-touch screen devices.
Due to gestures not having common functionality across different applications and devices
users need to remember the different potentially contradicting sets of gestures. This limits
the user’s ability to develop procedural memory.
Traditional gesture systems are scale variant leading to a user having to perform a gesture
at specific size for it to be recognised. This limits the transferability of a gesture across
different devices or applications.
Swype keyboard
Gestures performed on a swype keyboard are interpreted based on a path drawn by a user.
The system is error prone as a user is left to assume the correct way to perform a gesture.
Minimal indications of a user’s progress are provided to the user as they construct a gesture.
This can lead to unintended movements which can alter the result of the gesture. Due to a
user’s drawn path being used for determining the gesture, minor movements can lead to a
user’s gesture veering away from an intended word.
Using a swype keyboard requires the user’s attention to ensure they are entering the gesture
correctly in the small space provided. A user’s region of interest must be diverted to the
swype keyboard when they are using it.
The procedural memory developed for a swype keyboard can only be used on touch screen
devices.
A swype keyboard’s registrable words are not known until a user enters the full gesture. The
larger the vocabulary of words registerable via a swype keyboard the less accurate
neighbouring words become as they have similar gestures.
A user is ergonomically constrained when executing a gesture with a swype keyboard. A
swype keyboard requires predefined static regions for registering inputs. During performing a
gesture on a swype key, irrelevant keys must be carefully navigated around with a minimal
margin of error to ensure a gesture is correctly constructed. During the usage of a swype
keyboard a user’s finger may occlude the user’s view of the keys they need to interact with.

Screen gestures
Screen gestures have a limited vocabulary of functionality due to their being a limited
amount of directions a user can recognisably swipe. A user is uncertain of what functionality
will result from them using a swipe gesture unless it is contextually obvious. Typical screen
gesture systems do not offer a user a way to easily discover the available functionality.
Swipe gestures have affordance on touch screen devices where they seem natural. On other
platforms the effectiveness of a screen gesture is dependent on the quality of mouse or
trackpad a user is using.
## Dial
Dial based input systems are stateful which means the current location of the dial needs to
be taken into account before performing an input. It is difficult to develop procedural memory
on multiple incremental procedural inputs. The nature of a dial lends it towards being a more
effective input system for specific scenarios (e.g. volume controls) and less so for others.
(e.g. translating and selecting, where a mouse would be a better fit).
A physical dial requires a large surface area to be effective and ergonomic. Digital dials lack
the tactile sensations provided by a physical dial which affects a user’s accuracy when using
them.

The invention
How the invention solves the common UI problems:
Uses large amounts of screen space
Instead of requiring dedicated screen space for each function, CommandStick(CS) reuses
the same gesture space for all functions. Larger vocabularies of commands do not require a
larger screen space like buttons do, they result in longer gestures within the same gesture
space. The gesture space only needs to be large enough to discern between movement of
the finger in four cardinal directions, so it can be made only slightly larger than a finger.
Requires visual attention
CommandStick contains inventions to ensure the user is not required to look at CS’s user
interface, and away from their work. It can be used in unsighted tasks (e.g. issuing a
command in a pocket), in safety-critical environments (e.g. automobiles) or can be used to
increase productivity in tasks that require attention (e.g. computer applications like CAD)
-Items are always displayed in the same location on the CS display, allowing procedural
memory to be used to build up a signature gesture for each command, without looking at
their position in subsequent performances of the gesture.
-CommandStick is stateless. That means the user does not need to look at
CommandStick before performing a gesture to ascertain its state - every time they touch
CommandStick it responds the same way.
-Attention isn’t required to find CommandStick or ensure the finger’s position on it. The
user needn’t look at CS on larger screens, because the position of CommandStick on
the screen is always known because CommandStick can be summoned to the user’s
finger by double-tapping the screen, so every gesture starts at where the finger currently
is.
-CS provides non-visual feedback, such as vibration or sound, allowing the user to know
if an action has been performed correctly.
-Scale-independent, so the user does not need to know the size of CS when performing
a gesture.
## Slow
CommandStick contains inventions to make the execution of commands faster than other
UIs:
-Single touch - To reduce the time to enter an input, a single gesture is required for each
command, which needs only a single touch of the screen.
-Dial adjustment control - To reduce repetition (e.g zooming, scrolling, gestures can end
in a scroll gesture, allowing a quantity to be adjusted by rotating a finger like a dial,
around the periphery of the CS space.
-To reduce the time taken for finger movement, CS provides a small command space.
Gestures can be performed outside of the command space if a larger command space
with more control is required.
-To reduce the latency of performing a command in response to an event,
commonly-used commands can be made very short (e.g. a single up gesture).
Application-specific commands can also be made that are very short (e.g.the user may
program marcos). Furthermore, a gesture can be performed in advance of an expected
event, so that the function is ready as soon as the user lifts their finger - such a
pre-prepared gesture can be cancelled by dragging the finger to the middle.

Imposes a cognitive load
CS reduces the cognitive load of using the UI, releasing more of the user’s cognitive
faculties to perform their task.
-CS gestures are designed to be stored in procedural memory, leaving the other types of
memory usable by the task under work (e.g. episodic, declarative, visio-spatial
sketchpad, phonological loop etc). Procedural memory is typically not used in most
cognitive tasks so it can be freely used by the UI method, as proven by other successful
UI methods (e.g. touch-typing)
## Inexpressive
CS contains inventions to ensure it is expressive enough to enable a wide vocabulary of
commands.
-Long gestures - the length of gestures is in principle unlimited, allowing a range of
gestures limited only by the ability of the user to perform them. People regularly learn
very complicated gestures with dozens of steps (e.g. signatures, sign language,
body-language). A gesture with 6 movements has a vocabulary of 4,096 commands.
-Re-entrant gestures - gestures may re-use the same command activation areas,
increasing the options to 4 in each gesture.
Not usable one-handed
CS has inventions to allow it to be used one-handed.
-Single gesture - gestures are a single path, requiring only one movement
-Activation by lift - a gesture can be prepared in advance of an anticipated event, and
launched by simply releasing the finger. No additional gesture is needed to activate a
command
-One-finger - not only is CS designed to be used on-handed, all commands can be
issued by one finger.
-Excursion size - CS activation area is sized to the comfortable excursion of the finger of
a small hand. Larger hands still fit in this small space because gestures can be
performed outside the space, since CS is an angle-based input gesture system, so
distance from the centre can be varied by the user to suit their hand size.
Prone to errors
CS has inventions to ensure movements are easy to perform with the required precision.
-Large space between selectable items - items are arranged at the peripherals of the CS
circle, which is the largest separation possible for 4 items in a space. The large space
between items allows CS to be used on very small touch surfaces without input error -
there only needs to be enough space to discern whether a fingertip has moved in each
of the four cardinal directions - a minimum input surface may have only a few mm on
each side of a fingertip.
-Angular gestures - the human hand is more prone to translation error than rotational
error. Bumps and shakes produce translation errors, they do not rotate the person or
device.
-Threshold zones - CS provides movement thresholds before an input is registered.
These thresholds can provide generous excursion, allowing deviation or variability in
gestures. The thresholds may vary with path quality (e.g. be velocity sensitive) to allow
more confident users to activate with less excursion.
-Cancel - a user is able to cancel an erroneous gesture at any time by moving their finger
back to the cancel item in the centre. Unlike other input methods, errors are not
necessarily executed, the user has the ability to cancel them.
-Command feedback - CS indicates the command that would be executed if the user was
to release their finger at this moment. This is unlike other gesture systems (e.g. screen
swipes) where the user must guess the functionality.

-Trail - a trail is made of the finger's movement during a gesture, so that a user can see
any mistakes that have been made.
-Extending past border - gesture travel may extend outward past the outside border of
CS. Moving outward from the border increases the distance that a finger must travel
between selections, increasing the error margin. Thus, because CS is an angular control
system, it is insensitive to distance, so a user is able to arbitrarily select their desired
error margin during the performance of a gesture, by moving their finger closer or further
from the centre of CS.
-Each CS commands can be remembered as a single gesture / shape, which reduces
errors caused by remembering a large number of steps.
Have no error-checking
Unlike most UIs which execute actions immediately, CS contains error-checking inventions.
to allow a user to confirm whether the command selected by a gesture is as desired, or
erroneous, before executing it.
-Finger-up confirmation - A command isn’t executed until a user’s finger is raised
-Peek - CS can allow the application to preview the effect of a command. Previews are
possible because commands are selected by gesture, but only executed by releasing a
finger. Thus there is a point at which a command is selected but not issued. That
moment can be used to instruct an application to preview of the selected command (e.g.
the ‘delete’ command may show how the scene would look if an object has been
deleted), if the effect is as desired, the user may then lift their finger to execute the
command or move their finger to the centre to cancel it
-Path display overlay - a menu of possible commands may be displayed, and a selected
command may be overlaid on the previous command, so that it is possible for a user to
see where their path was incorrect.
Difficult to diagnose input errors
CS contains inventions to help users see when they make an error, and to understand what
went wrong.
-Continuous gesture resolution - As the user performs the gesture, it is continuously
evaluated and the currently interpreted command (based on the path so far) is
displayed, allowing the user to see when part of the gesture path has been missed (e.g.
the user’s path has selected “edit” commands rather than “zoom”)
-Path display - the path of a gesture is displayed, allowing the user to see when an
incorrect gesture shape has resulted in an error.
-Removal of commands that cannot be selected - only options that can be selected are
shown to the user, based on the gesture path so far
-Vibration - vibration may be used to indicate the activation of a zone. A signature
vibration may be used for each zone.  The cadence of these vibrations may result in a
“signature vibration” that allows the user to recognize by feel whether a command has
been correctly performed
-Sound - activations may have a signature sound, so the user is able to recognize by
sound whether a command has been correctly performed
-Menu - a menu of commands may be provided, displaying the gestures to be performed
-Desired path overlay - if a command is chosen in the menu, it may be overlaid on the
user’s last command, to show where the user’s gesture deviated. Optionally, the desired
path and user path may be shown at the completion of a gesture, so the user is able to
see how their command gesture may be improved or optimised.

Difficult to learn
CS has inventions that allow it to be easy to learn
-Designed for procedural memory - CS is optimised for the type of human memory called
“procedural memory”. Procedural memory is learned by the repetition of tasks, so CS
gesture commands are taught by encouraging the user to follow a path until the path is
learned as a gesture. The path does not include the ability to go back, as this would no
longer be repetition - the user is required to perform the task again, encouraging
repetition.
-Designed for auditory loop memory - human auditory memory can store up to 7 recently
heard items. CS can introduce commands as a sequence of sounds that the user can
reproduce by performing the activation sounds to produce the gestures.
-Universal gestures - A selection of CS commands are selected as “universal”, allowing
them to be present on any device that has a CS control, reducing the difficulty of
learning a new device. Non-universal commands are gated by specific gesture (e.g.
swiping downward or using two fingers to perform the gesture)
-Designed to be apparent. CS displays all possible commands at all times, without
cluttering the UI, by grouping commands into menus. This principle of CS makes it easy
to learn: that there are no commands possible that are not represented on the screen.
-Intuitive gestures - CS command gestures can be chosen to be representative of
real-world gestures - for example the gesture of “back” could involve swiping the finger
backward.
-Grouped gestures - commands that are related may have gestures with a common
beginning (e.g. copy and paste may start with a common gesture that means
“clipboard”, followed by a gesture that specifically means “copy” or “paste”). These
common beginnings naturally correspond to menus, making them apparent and easy to
learn.
-The CS design has inventions to provide affordance so that new users can intuit what to
do. The central part of the CS control space has a circle in the centre that shows a new
user where to begin a gesture. The circle moves with the user’s finger, demonstrating
that the control is responding to user input. The circle continues to follow the user’s
finger outside the circle, indicating that their input is still valid. The circle may refuse to
follow the user’s finger past the end of possible valid commands, to indicate the
invalidity of further input. The circle may also display the status of the current command,
by changing shape (e.g. a splash shape to represent the passing of a selection
threshold). The shape is sized to be large enough to be visible around the user’s finger,
as the finger presses on the screen
-CS has inventions so that experienced users do not need to reference the user
interface’s text or instructions once the user is experienced. The path to each instruction
is a single continuous gesture, so experienced users do not need to remember the steps
that build up the gesture. CS contains an “expert mode” where the UI elements are
conditionally hidden based on the interpreted confidence of the user at using CS. Hiding
the UI elements declutters the user’s screen and frees up screen real-estate.
-Consistent - CS has a set of design rules that are consistently enforced, so that users
who are familiar with one part of CS’s UI can quickly become proficient at unfamiliar
parts. Those design rules are:
-All commands are a single gesture
-All possible command are apparent at all times (no hidden functionality)
-All things that are shown can be immediately selected
-CS is not modal, so all commands may be performed at any time
-Commands are angular, not distance sensitive
-All commands may be performed by a single hand
-No silent activation - all selections are demonstrated
-Fault tolerant gestures - all gestures result in a valid command
-Cancellability - all gestures can be cancelled.
-Speed - all functionality must be easy to execute

-Hone-able - all commands are hone-able and be performed more efficiently
-Command List - a guide containing all of the possible gestures can be made available. It
may be made available in response via a menu, or in response to input patterns that
suggest the user is uncertain how to use CS (e.g. multiple cancelled gestures)
Unnatural motion
CS has inventions to ensure that the motion of using it is natural and comfortable.
-Hands are more accurate at rotation - the human hand has positional accuracy of
12.7mm and orientation repeatability of 9º. For small interfaces (<25mm), human
positional inaccuracy is 50%, while human rotational inaccuracy is only 2.5%. This is
why CS is based on rotation, not positional accuracy.
-Continuous gestures that utilise one hand fine-motor control - the human hand has
fine-motor control that is not used in other input methods such as keyboards, that use
discrete, binary inputs. CS also uses fine-motor rotational hand capabilities for rotational
adjustment of selected commands (e.g.volume, zoom)
-Natural range - The human finger has a comfortable excursion range that is smaller than
the screen of a smartphone. Research in 2016
(https://pubmed.ncbi.nlm.nih.gov/26943492/) has found that interaction regions of
commercialised smartphones should be lowered 20 to 30 mm for more comfortable
interaction. CS provides a touch space that is sized within the comfortable human finger
range.
Difficult to see
-Multi-functionality from the same UI space - All commands use the same input-space, so
the input features can be reused, so there is no need for different UI elements for each
situation. In order to make the UI space reusable, CS makes several inventions:
-CS Menu items change during a gesture - so that the options available to be selected
are scoped by menu selections up to this point
-Gesture path history allows re-use - the path up until now defines the context and
meaning of any future part of the gesture. For example whether the initial part of the
gesture enabled the zoom menu or volume menu.
-Gestures can be re-entrant - gestures may repeat parts of themselves because the
meaning of each movement changes with its history.
-User interface elements require small labels because there are many or they are not
otherwise readily identifiable.
## Beautiful
CS contains inventions to make it beautiful to perform and observe (e.g typing)
-Fluency - forms of communication designed for beauty such as calligraphy and the
performing arts, are composed of continuous curves. CS uses continuous curves to
compose commands, and displays those curves
-Symmetry - the CS UI space is symmetrical vertically, horizontally and rotationally. The
inner cycle also symmetrically echoes the outer circle
-Minimal - people find beauty and serenity in uncluttered spaces. CS displays only a
minimal single item per direction.
Hand occlusion
CS contains inventions to ensure the hand or finger that is operating the user interface does
not occlude the input method
-labels at the periphery - selectable items are arranged at peripheries of the user
interface
-Four directions - each individually labelled.
-Activation shape surrounds finger

-Activation thresholds - activation thresholds allow a user to move their finger to
investigate a label that is occluded, without fear of accidentally activating an option.
Large separation
CS contains inventions to ensure that it is not distant from the work, removing the need for
large gaze distance/ refocusing between input and work.
-Summoning - CS can be summoned to the location of the work by double-tapping
-Small size - CS is small enough that it can be placed alongside the work
-Re-sizable - the CS input surface can be re-sized so that it does not occlude the work
-Transparency - CS can be made partially transparent. In particular, the gesture space
can be made transparent, because the commands are in the periphery
Not general purpose
CS contains inventions to make it suitable for a wide range of tasks:
-Universal gestures - a set of gestures are common to all usages of CS, so that gestures
memorised (e.g. for zoom) in one application can be used everywhere that CS is used.
So the skills learned in one task can be generalised to other tasks.
-Application-specific gestures - gestures can be made for application-specific
functionality. Application-specific gestures make it possible for CS to be used for any
application.
-Custom gestures - users may configure their own gestures, using gestures that are not
reserved for custom or application-specific gestures.
-Range of input technologies - CS can be implemented as a touch screen, a
mouse-controlled screen, a rotary dial, a click-dial, arrow keys on a keyboard,
screenless devices, rotatable watch bezels etc
Ambiguous recipient
CS has inventions to remove ambiguity about what the recipient/target
-Centre target - at rest, the centre of CS displays a logo indicating the recipient of the CS
commands
-Focus indication - CS indicates which on-screen element(s) will be affected by the
command.
-Preview - CS allows commands to be previewed before they are actioned. This can be
used to remove any ambiguity about which device or control is being modulated
-Dedicated command space - CS has a dedicated area that all CS gestures begin in, so
there is no ambiguity about whether this really is a CS gesture.

## Secondary Inventions
Every new invention has a range of side-effects that require new inventions to solve them.
CS has a range of issues that required inventions to solve:
New vocabulary to learn
A new UI must not only solve the problems that existing UIs have, it must also solve
additional challenges related to acceptance. Large lists of functions are hard to learn. CS
has hundreds of command gestures, and all of them are new to a user. Each of the
hundreds of command gestures consists of many movements, so in total there are
thousands of new things to remember, to become proficient at CS.
## Unfamiliarity
A challenge that CS presents is that users are unfamiliar with the input method
Initial slowness
The problem; users are slower at using unfamiliar input methods, so they are reluctant to
use new methods and prefer to use existing well-known methods that they are proficient in.
Solutions:CS has inventions to overcome this initialunfamiliarity:
Instruction clutters the UI, making it unattractive and unlikely to be used.
All commands are initially unfamiliar, so require instruction, But the presence of instruction
clutters the UI, making it unattractive. The attractiveness of a UI is most important in the first
moments that a new user encounters it, which is also the time they need the most
instruction. Paradoxically, instruction makes a UI moreusable, but also less likelyto be
used. Instruction not desired once familiarity isestablished.
●Paradigm- the new UI presents a challenge of how itworks (e.g. what parts should me
oved, what happens if they are moved?) should try to use a paradigm that is familiar to
the user, from other UIs or from other universal aspects of experience
●Cognitive load- learning a new system imposes a cognitiveload that detracts from the
task at hand
●Unobvious benefits- designers and users are unlikelyto invest the time in
implementing or learning to use a UI unless it has obvious benefits.
Commands and menus coexist | Commands and menu do not align
CS is designed to be apparent, so it displays all possible commands at all times by grouping
commands into menus. But some commonly-used commands should be short (e.g. “back”
may be a single swipe left, “forward” swipe right) which would leave few cardinal directions
for menus.
Solutions:CS makes it possible for commands and menusto co-exist in a single direction,
by making a gesture that ends in a direction be a command, and a gesture that continues on
from this direction be a menu. This requires a display method that can display both a menu
and a command at the same cardinal direction. CS provides several ways to make this dual
display happen. In the first method, the menu name is displayed near the cardinal direction
with text. An icon is also placed near the indicated menu name to indicate the function which
would be selected as a result of a user gesturing in the cardinal direction.
In another method functionality for switching the set of functions used for interpreting the
gestures is provided. A user can then perform an action to switch between function sets.
Different function sets can offer different functionality on the short commands (e.g. swipe left
corresponding with the “back” function in one function set and swipe left corresponding with
the “Edit” menu in another).

Many steps to learn for each gesture
CS can house many gestures, each gesture having the potential to be very long. This
capability places a large burden on a user to memorise the available functionality.
Solutions:CS solves this memorisation burden by providingfully guided gesture construction
experience. At each step of the construction of a gesture a user is presented with a visual
indication. The visual indication indicates to the user how they should proceed to construct
their gesture if they intend to select a specific function.
Gestures are hard to remember when shown as a list or visually as a squiggle
Solutions:CS has inventions which allow a user tocontinuously receive guidance as they
interact with the input system. This removes the burden for a user to have to remember
gestures as the input system usage is guided.
Cannot correct errors
CS is designed to encourage a user to build procedural memory through performing
repetitive gestures. To optimise for this procedural memory development strategy “undo” or
“back” options are not available during gesture construction. This can lead to scenarios
where a user has constructed a gesture which selects an undesired function.
Solutions:CS has inventions to indicate to a userwhen they have selected an undesired
function and to allow them to cancel the execution of that undesired function.
Double-tap is already used for other things than summon
Many applications use double-tap to perform actions. Summoning CS in this circumstance
would be difficult.
Solutions:CS implements inventions which allow auser to summon CS through other
means such as clicking a button within a menu or pressing a key on a keyboard. The
summoning location of CS would be anchored around the location of the user’s cursor or
some other predefined location in an application.
Difficult to make it apparent that re-entrant gestures are possible
Indicating to a user that they are able to register a gesture twice is complicated due to the
user interface displaying the currently selected function in the location where a potential
future gesture would be indicated.
Solutions:CS implements visual hints which indicateto a user that additional functionality
exists.
Activation difficult to confirm without visual display
When interacting with CS, a user may struggle to determine that the system has registered
his input as their finger/ hand may be occluding their view of the input system.
Solutions:CS has inventions which utilise hapticfeedback and auditory feedback to indicate
to the user that the system has registered an input.
Difficult to show new users that they can use the screen outside of CS
As a user interacts with CS it is not apparent that the input system is capable of registering
the user’s input when they move their pointer outside the boundaries of the input system.
Solutions:Inventions have been implemented to solvethis problem. When a user gestures
beyond the input system’s boundaries, a visual indicator tracks the location of a user’s
pointer. A user can start a gesture within the boundaries of the input system and see the
visual indicator follow them as they go beyond the boundaries of the input system.

Gestures are static but menus are dynamic, so depicted gestures cannot show
the menus it went through
Solutions:The contents of a menu are arranged tobe related to the name of the menu that a
user interacted with. This lessens the burden on the user to remember the menu name as
the available functionality within a menu can be used to infer the name of the menu.
Instructions / Command list must be selected using a CS gesture, but user
can’t know the gesture to select it
CS instruction guide and command list functionality can only be selected through a gesture.
This leads to a scenario where a user requires the guide to find out which gesture opens the
guide.
Solutions:An invention has been implemented whichtracks a user’s cancelled commands
data and uses that data to determine when to automatically open the guide.
CS gets in the way after it has performed a command
CS being summonable means that a user can bring it to their current region of interest and
more efficiently execute a command without diverting their gaze. After using CS it’s presence
detracts from the user’s ability to focus on the prior region of interest.
Solutions:CS has inventions which allow it to bedismissed by double click or perform an
action on CS.
CS is a totally new UI that users will be unfamiliar with
Solutions:Several inventions exist which make itmore approachable to new users:
●Borrowing paradigms from gesture systems and menus
●Continuous guided execution - The system continuously guides a user through the
available options until they reach their desired function.
●Explicit command execution - Commands are only executed in response to a user lifting
their finger.
●Anytime cancellation - A user can cancel the execution of their selected function at any
time.
●Bite size - CS offers four options at time for a user to select from. Each option being
clearly labelled.
Procedural memory transferability
Different screen sizes and zoom levels lead to CS being interacted with at different scales.
This lowers the transferability of a user’s procedural memory.
Solutions:CS has inventions which allow for the user’sinput to be dynamically adjusted
based on the interpreted scale of CS. This invention allows for the consistent registering of
gestures across different screen sizes and zoom levels.
Long activation excursion on mobile whilst typing
Accessing CS whilst typing on a mobile keyboard requires a user to make a strenuous
excursion past the mobile keyboard. When a user is typing and intends to access CS’
functionality the height of the mobile keyboard is a barrier.
Solutions:CS has inventions which allow it to beaccessed within the same screen space as
a mobile keyboard. This is achieved through holding down a key within the mobile keyboard
and swiping to activate CS. When activated CS is superimposed over the mobile keyboard.

Unresolvable gestures waste a user’s time and cause confusion
A user can attempt to construct a gesture resulting in a gesture which does not correspond
with a function.
Solutions:CS has inventions which prevent it fromregistering inputs which lead to
unresolvable gestures. If a user registers an input which does not bring them incrementally
closer to a valid function it is disregarded. This results in an input system in which all
gestures correspond with a function.
A user is unaware of at what point their gesture diverged into being
unrecognisable
Solutions:Providing a user with an indication ofan aspect of their gesture which leads to
their constructed gesture being unrecognisable. The aspect of a gesture which leads to the
divergence can then be observed by a user and noted when they re-attempt a gesture.
A function (e.g. universal copy) may not be available under a certain context
Universal functions are indicated across all platforms/ applications but developers may not
necessarily incorporate a specific universal function into a platform/ application. This leads to
scenarios where a user can select a universal function which is not available.
Solutions:An indication is provided to a user priorto them attempting to execute it. The
indication would communicate whether an indicated function is available.
Balancing the riskiness of a function with the ease of execution
Balancing the riskiness of a function with the ease of its execution can lead to risky functions
being easy to execute. Commands within the input system should be as easy to perform as
possible, however functionality such as “delete” may need to be harder to perform to avoid
the accidental execution of a function.
Solution:An invention is implemented which providesa buffer between the immediate
execution of a function. A user must provide additional confirmation of the execution of a
function.
Maintaining a compact gesture space as the number of functions grows
Each indication option within a gesture space needs to be carefully selected due to there
only being four options visible at a time. Providing togglable functionality within  gesture
space leads to two options being taken up. (e.g. “swipe up” being “turn on light” and “swipe
down” being “turn off light”)
Solutions:An invention is implemented which conditionallychanges a function’s identifier
based on the internal state of the system. (e.g. “turn on X” turns to “turn off X”)
## Group Labels
Having unassociated commands in proximity to each other forces a user to have to
remember the individual location of commands.
Solutions:Grouping commands and having labels allowsa user to just remember the
gesture corresponding with the group instead of the gesture corresponding with the
individual functions. Function group labels also enable a user to not have to check every
gesture route; a user is able to anticipate the contents of a gesture route by reading the
group label.

Dial control performance is indistinguishable from a gesture
A difficulty arising from CS occurs at the conclusion of applicable gestures, where a dial
control may be displayed to allow the user to adjust the quantity that has been selected (e.g.
zoom, volume). The difficulty is that the completion of a command requires the user to lift
their finger, otherwise the command would be perceived as incomplete and may be
interpreted as a menu, so the beginning of a dial adjustment starts with a new touch. This
new touch presents problems, because the beginning of dial movement looks identical to the
beginning of a new gesture, and CS must discern between the two possibilities. It also
presents the problem that CS becomes stateful, because the interpretation of a gesture as a
dial gesture or command gesture depends on the gesture that was performed before it.
Solutions: One invented solution is that dial control gestures may be distinguished from
command gestures because dial gestures begin at the periphery of the CS control. CS
commands always begin in the circle at the centre of the CS control. This solution is simple
but it is still stateful.
Another invented solution for discerning dial gestures from command gestures is that two
fingers may be used at opposite sides of the CS control, analogous to the way fingers are
placed when turning a knob, so it is intuitive. The method also does not require statefulness,
because the user changes from command gesture to dial control gesture by placing a
second finger on the dial. Releasing both fingers reverts to the single normal state, where all
new commands are treated identically. However, the dual touch solution has problems,
because multiple-finger touch is not available in all input modalities, the ability to use a
second finger in this way is not apparent to the user, and the method occupies the semantic
meaning of two-finger touch, so two-finger touch cannot be used to indicate other meanings.
An inventive solution combines the other two solutions to remove their shortcomings: two
finger touch is used for dial adjustment, and made possible in traditional single-input
modalities by using the right mouse button or an adjacent physical key/button. Dual finger
adjustment is made apparent to the user by displaying a second small circle on the opposite
side of the CS circle, indicating where a finger could be placed to execute the command and
begin the adjustment process. The method is prevented from interfering with other meanings
of two-finger touch by only being enabled in the specific circumstance that the user places
their second finger in the circle on the opposite side of the dial, and rotates both fingers in
the same direction.
Finger occludes the display
A difficulty arises when using menus to learn  to perform a gesture, because the user can’t
see the item their gesture is selecting, and can’t see when it has been activated
Solutions:Using a back surface (touch surface, touchscreen, folded touch screen) to access
CS. Allowing CS to be used without a user occluding their vision of the UI.
